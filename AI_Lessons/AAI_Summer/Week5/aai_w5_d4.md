Lesson Plan: Applied AI Week 5, Day 4 --- READMEs, Tech Docs, and Product Documentation
=====================================================================================

**Duration:**
-------------

3 hours

**Lesson Overview:**
--------------------

On Day 4, Geniuses focus on one of the most important parts of making a venture real and capstone-ready: **documentation**. After defining venture vision, business models, and prototypes, Geniuses now learn how to explain their product clearly to different audiences. This lesson covers **README files, product documentation, technical documentation, setup instructions, features, roadmap thinking, and communication for collaborators, judges, and future users**.

The core idea of the lesson is that strong builders do not only make products. They make their work understandable. A strong README helps someone know what the project is, why it matters, how to run it, and where it is going next. Strong documentation also helps Geniuses work more independently during capstone weeks. During guided practice, the class builds a GitHub-ready `README.md` and a simple `TECHNICAL_DOC.md` for a venture prototype. During independent practice, each Genius creates documentation for their own capstone venture so that the product, business case, and technical setup are easier to understand and continue building.

**Objectives:**
---------------

-   Explain what a README is and why it matters in technical and venture work.
-   Distinguish between product documentation and technical documentation.
-   Identify the sections of a strong GitHub-ready `README.md`.
-   Write clear setup instructions, feature descriptions, and usage notes.
-   Create both a `README.md` and a `TECHNICAL_DOC.md` for a capstone venture.
-   Reflect on how documentation supports teamwork, pitching, and independent building.

**Materials:**
--------------

-   Laptops for all Geniuses
-   VS Code installed
-   Internet access
-   Projector or display
-   Whiteboard and markers
-   Slide deck for lecture and discussion
-   Reflection journal or digital notes
-   Existing venture documents from Days 1--3
-   Existing prototype files from Day 3
-   Starter folder for documentation files
-   Markdown preview in VS Code

**Standards:**
--------------

-   Computational Thinking: Organize technical and product information into clear structures for reuse and collaboration.
-   Computer Science Practices: Document systems, setup, and decisions so others can understand and build on the work.
-   Technical Communication: Write clearly for multiple audiences including teammates, users, and reviewers.
-   Digital Literacy: Evaluate how documentation improves access, clarity, and continuity.
-   Career Readiness: Practice written communication, organization, and professional project presentation.
-   Entrepreneurship and Innovation: Create clear venture documentation that supports product understanding and growth.

**Lesson Activity:**
--------------------

### 1. **Introduction (Time: 25 minutes)**

-   **Objective:** Energize Geniuses and introduce the idea that great work is not enough if nobody can understand, run, or continue it.
-   Start with an icebreaker called **"Could Someone Else Use This?"**
-   This should be the first thing and the most fun thing to wake Geniuses up and get them ready for the lesson.

#### **Icebreaker Option A: Physical Movement**

-   Label one side of the room **"Clear Enough"** and the other side **"Needs Better Docs."**
-   Read project situations aloud and have Geniuses move to the side that best matches.
-   Example prompts:
    -   A project has a strong prototype but no explanation of what it does
    -   A project has setup steps, feature descriptions, and a mission statement
    -   A project uses an API but never explains how to add the key
    -   A project has screenshots but no instructions
    -   A project explains who it is for, how to run it, and what is still unfinished
    -   A project has great code but no README at all
    -   A project has a README, but the wording is vague and generic
-   After each round, ask:
    -   What makes this clear enough?
    -   What would a new builder or judge still need?
    -   Why do docs matter even if the product looks good?
    -   What would frustrate someone trying to run this project?

#### **Icebreaker Option B: README Critique**

-   Show two short README openings:
    -   one vague
    -   one clear
-   Ask Geniuses:
    -   Which one makes you trust the project more?
    -   Which one makes the product easier to understand?
    -   What is missing from the weak version?

#### **Transition**

-   Say:
    -   "A README is not extra. It is part of the product."
-   Ask:
    -   If someone opened your capstone project today, what would they understand right away?
    -   What would still confuse them?

### 2. **Direct Instruction (Time: 50 minutes)**

-   **Objective:** Help Geniuses understand documentation types, audiences, and how strong documentation supports real product development.
-   Use slides to guide instruction and pause often for discussion.

#### **Suggested Slide Flow**

-   **Slide 1: Day 4 Focus --- Make the Venture Understandable**
    -   Today is about writing documentation that supports clarity, continuation, and presentation
-   **Slide 2: What Is a README?**
    -   A README is the front door to a project
    -   It helps people understand:
        -   what the project is
        -   why it exists
        -   how to run it
        -   what it includes
        -   what comes next
-   **Slide 3: Why READMEs Matter**
    -   They help collaborators
    -   They help judges and reviewers
    -   They help facilitators
    -   They help future-you
    -   They make projects easier to continue and improve
-   **Slide 4: What Makes a Strong README**
    -   clear title
    -   strong project summary
    -   problem and audience
    -   feature list
    -   setup instructions
    -   usage explanation
    -   tech stack
    -   roadmap or next steps
-   **Slide 5: Product Docs vs Technical Docs**
    -   **Product docs** explain:
        -   purpose
        -   user
        -   value
        -   features
        -   mission
    -   **Technical docs** explain:
        -   setup
        -   stack
        -   files
        -   APIs
        -   architecture
        -   known issues
-   **Slide 6: Who Are You Writing For?**
    -   a teammate
    -   a facilitator
    -   a judge
    -   a mentor
    -   a future builder
    -   yourself later
-   **Slide 7: Common Documentation Mistakes**
    -   too vague
    -   missing setup steps
    -   no explanation of the product
    -   no mention of the audience
    -   no note about unfinished features
    -   no clear tech stack
-   **Slide 8: Helpful Sections for Capstones**
    -   project title
    -   one-sentence pitch
    -   problem
    -   users
    -   features
    -   screenshots or demo notes
    -   installation
    -   usage
    -   roadmap
    -   future plans
-   **Slide 9: Technical Docs Support Independence**
    -   capstone weeks go smoother when the project is clearly documented
    -   docs help teams and individuals move with less confusion
-   **Slide 10: Day 4 Goal**
    -   create a README and technical doc that make the venture easier to understand, continue, and present

#### **Discussion Questions**

-   Why does a project need both code and explanation?
-   What makes a README useful instead of just long?
-   Why should product purpose appear in technical documentation?
-   What is the difference between "what it does" and "how it works"?
-   How does documentation help during capstone work?

#### **Reflection Prompt**

-   Have Geniuses write for 4 minutes:
    -   "If someone opened your project right now, what three things would they need explained first?"

### 3. **Guided Practice (Time: 55 minutes)**

-   **Objective:** Help Geniuses create a strong `README.md` and a basic `TECHNICAL_DOC.md` for a venture prototype.
-   Explain that today's guided practice is about writing for clarity and continuity.

#### **Guided Practice Build**

Create a folder called `venture-docs`.

#### **Project Goal**

Build:

-   a GitHub-ready `README.md`
-   a `TECHNICAL_DOC.md`

#### **Setup Steps**

1.  Open VS Code.
2.  Create a folder called `venture-docs`.
3.  Inside the folder, create:
    -   `README.md`
    -   `TECHNICAL_DOC.md`
    -   optional `doc_prompts.js`
4.  Open Markdown preview in VS Code.

#### **Sample `README.md`**
```
# BridgePath AI

BridgePath AI is an AI-powered career support platform designed to help high school Geniuses explore career pathways, prepare for internships, and organize their next steps with accessible guidance.

## Problem
Many Geniuses do not have easy access to clear, personalized career support, mentorship, or opportunity navigation tools.

## Who It Serves
- High school Geniuses
- First-generation students
- Schools and youth development programs

## Why It Matters
BridgePath AI is built to make career guidance more accessible, more personalized, and more actionable for Geniuses who may not already have strong professional networks.

## Features
- Career interest input flow
- Suggested career directions
- Next-step guidance
- AI-supported support experience
- Mission-driven venture prototype

## Tech Stack
- HTML
- CSS
- JavaScript
- Optional Node/OpenAI API integration

## How to Run
1. Clone or download the project files
2. Open the folder in VS Code
3. Open `index.html` in Live Server or your browser
4. If using backend features, install dependencies and add your `.env` file

## Current Status
This is a capstone venture prototype in active development.

## Roadmap
- Improve prototype interactions
- Add stronger user personalization
- Expand career support workflows
- Add partnership and school-facing features

## Venture Vision
BridgePath AI exists to help more Geniuses access confidence, clarity, and direction as they prepare for future opportunities.
```
#### **Sample `TECHNICAL_DOC.md`**
```
# Technical Documentation: BridgePath AI

## Project Type
Mission-driven AI venture prototype

## Core Purpose
BridgePath AI helps Geniuses explore careers, prepare for opportunities, and organize next steps through an accessible AI-supported experience.

## Main Files
- `index.html` --- main prototype page
- `style.css` --- styling and layout
- `script.js` --- front-end interactivity
- `server.js` --- optional backend logic if OpenAI integration is added
- `.env` --- stores API keys securely if backend is used

## Key Features
- Hero section with value proposition
- Problem and mission explanation
- User journey section
- Interactive demo section
- Trust and mission-oriented messaging

## Setup Notes
### Frontend Only
- Open `index.html` with Live Server or in the browser

### If Using Node and OpenAI
1. Run `npm install`
2. Create a `.env` file
3. Add `OPENAI_API_KEY=your_key_here`
4. Run `node server.js`

## Known Limitations
- Prototype does not yet include full production backend logic
- Output may still be simulated in front-end mode
- Personalization is limited in the current version

## Next Technical Priorities
- Improve backend integration
- Strengthen input validation
- Improve structured outputs
- Add user account or saved history features later

## Notes for Future Builders
Keep the venture mission centered in product decisions. Product clarity, accessibility, and trust matter as much as technical growth.
```

### 4. **Independent Practice (Time: 30 minutes)**

-   **Objective:** Geniuses independently create capstone-ready project documentation for their venture.
-   This continues the Week 5 mini-project.

#### **Mini-Project Title**

**Capstone Venture Package --- Day 4 README and Documentation**

#### **Independent Task**

Each Genius creates:

-   a `README.md`
-   a `TECHNICAL_DOC.md`

Their files must clearly explain:

-   what the venture is
-   what problem it solves
-   who it serves
-   what features exist
-   how to run the prototype
-   what tools or stack are used
-   what still needs work
-   what is planned next

#### **Required Deliverables**

-   A completed `README.md`
-   A completed `TECHNICAL_DOC.md`
-   Optional `doc_prompts.js` or helper file if useful
-   Documentation that includes:
    -   title
    -   summary
    -   problem
    -   users
    -   features
    -   setup
    -   tech stack
    -   roadmap
-   A short written reflection:
    -   What part of your documentation feels strongest?
    -   What still needs to be clarified?
    -   How will these docs help during capstone weeks?

#### **Facilitator Support Moves**

-   Help Geniuses write clearly and specifically
-   Ask:
    -   Would a new person understand the project from the first paragraph?
    -   Are the setup steps complete?
    -   Is the mission visible, not buried?
    -   Are you honest about what still needs work?
-   Encourage strong headings and readable sections

### 5. **Closure (Time: 20 minutes)**

-   **Objective:** Reinforce that documentation is part of product quality and venture readiness.
-   Bring the class together for a final share-out.
-   Ask 3--5 Geniuses to share:
    -   their venture name
    -   one README section they are proud of
    -   one technical detail they documented
    -   one way documentation will help them during capstone
-   Lead a closing discussion:
    -   What makes documentation useful?
    -   Why should builders document unfinished work too?
    -   How do docs support stronger teamwork and independence?
-   Preview the next lesson:
    -   Geniuses will work on subscriptions, pricing, pitch readiness, and capstone launch preparation.

**Reflection / Takeaways:**
---------------------------

This lesson works best when Geniuses realize that documentation is not separate from product quality. It is part of how a venture becomes understandable, collaborative, and sustainable. Day 4 helps Geniuses prepare for capstone weeks by making their work easier to continue, explain, and improve. By the end of the lesson, they should feel that their project is not only more complete technically, but also more professional and more ready for independent work.

---------------------

-   Reinforce that concise, clear writing is stronger than overly complicated writing.
-   Encourage honesty in documentation about what exists and what is still in progress.
-   Help Geniuses think about both judges and future builders as audiences.
